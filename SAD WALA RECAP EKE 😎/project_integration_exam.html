What is Project Integration?

  • Combining all requirements, assumptions, business rules, and models into ONE consistent package
  • Package used by designers, developers, testers, and users
  • Without integration: scattered requirements, misunderstandings, rework
  • Creates a single source of truth
  • Bridges analysis and design phases
⚠️

Problems Without Integration

  • Requirements stay scattered in notes, emails, interviews, diagrams
  • Developers misunderstand what to build
  • Testers cannot verify expected behavior
  • Users complain system doesn't match business needs
  • Scope creep increases
  • Rework becomes expensive
✅

Benefits of Proper Integration

  • Creates a single source of truth
  • Ensures consistency among models and requirements
  • Improves stakeholder communication
  • Supports design, development, and testing
  • Reduces ambiguity and rework
  • Helps project planning and estimation
  • Improves traceability: need → requirement → design → test
📋

System Specification Document

  • Formal document describing what is to be built
  • Also called: SRS / System Definition / Requirements Specification
  • Describes: what to build, what it must do, constraints, data, user interaction, quality attributes
  • Audience: users, analysts, designers, developers, testers, PMs, auditors
  • Serves as communication AND control document
🔍

Traceability

  • Links requirements to their sources and downstream deliverables
  • Requirement ↔ Stakeholder need
  • Requirement ↔ Use case / model
  • Requirement ↔ Design component
  • Requirement ↔ Test case
  • Requirement ↔ Change request
🏆

MoSCoW Prioritization

  • Must have — non-negotiable core requirements
  • Should have — important but not critical for launch
  • Could have — nice-to-have if time/budget allows
  • Won't have (this release) — explicitly out of scope now
  • Also: Business value vs effort, Risk-based, Regulatory priority
  • Used because not everything can be delivered at once
⚔️

Conflict Types in Requirements

  • Stakeholder conflicts — strict control vs flexibility
  • Process conflicts — different dept procedures
  • Terminology conflicts — same term, different meanings
  • Model-text conflicts — diagram ≠ written requirement
  • Scope conflicts — future features listed as current
📊

Good Requirement Characteristics

  • Clear — no ambiguity in meaning
  • Specific — precise, not vague
  • Unambiguous — one interpretation only
  • Feasible — can be implemented
  • Testable / Verifiable — can be confirmed
  • Relevant — tied to business need
  • Traceable — linked to source and tests
  • Consistent — no contradictions
Integration Content

What Is Being Integrated?

Seven categories of artifacts that must be combined into the integrated package.

A

Business Requirements

Business goals, expected outcomes, business problems to solve, and success criteria.

B

Functional Requirements

What the system must do: processes, services, features, inputs, processing, and outputs.

C

Non-Functional Requirements

Performance, security, usability, reliability, scalability, compliance, maintainability.

D

Business Rules

Policies, decision logic, constraints, approval rules, and calculations the system must enforce.

E

Models

Use case models, Activity diagrams, DFDs, ERD/data models, Sequence diagrams, UI wireframes, CRUD matrices, state-based logic.

F

Assumptions and Constraints

Budget constraints, technology stack, legal constraints, deadlines, integration constraints with existing systems.

G

Scope Definition

In-scope functions, out-of-scope items, defined releases and phases of the project.

👥

Who Uses the Integrated Package?

  • Designers — to create the system architecture and UI
  • Developers — to build the correct system
  • Testers — to verify expected behavior against requirements
  • Users — to confirm the system matches business needs
  • Project Managers — for planning, estimation, and tracking
  • Auditors / QA Reviewers — for governance and quality assurance

Key Deliverable

System Specification Document

The formal output of project integration — understand its purpose and audience.

📄

What It Describes

  • What system is to be built
  • What it must do (functional behavior)
  • What constraints apply
  • What data it uses
  • How users interact with it
  • What quality attributes it must satisfy
🎯

Purpose of the Spec Doc

  • Communicate agreed requirements clearly
  • Provide baseline for design and implementation
  • Support testing and acceptance criteria
  • Reduce misunderstandings
  • Enable project estimation and planning
  • Support maintenance and future enhancements
  • Provide evidence for governance/QA reviews
👥

Audience / Who Uses It

  • Users — confirm it meets their needs
  • Analysts — as the master record of requirements
  • Designers — translate to technical specifications
  • Developers — build what is specified
  • Testers — create test cases from it
  • Project Managers — plan and track against it
  • Auditors / QA Reviewers — verify quality and compliance
📛

Other Names for the Spec Doc

  • SRS — System Requirements Specification
  • System Definition
  • Requirements Specification
  • Business Requirements Document (BRD)
  • Functional Specification Document (FSD)
  • Name varies by organization — content is what matters

Good vs Poor Requirement Examples

❌ Poor: "System should be user friendly."
✅ Better: "New users should complete the student registration task without training, using on-screen guidance and validation messages."
❌ Poor: "System should be secure."
✅ Better: "The system shall enforce role-based access control and require authenticated login before accessing student academic records."
❌ Poor: "Reports should be fast."
✅ Better: "The monthly attendance report shall be generated and available to download within 5 seconds of user request."
❌ Poor: "The system should handle many users."
✅ Better: "The system shall support a minimum of 500 concurrent users without degradation in response time below 3 seconds."
