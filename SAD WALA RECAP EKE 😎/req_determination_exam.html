What Are Requirements?

  • Statement of what the system must do or must have
  • Describe system behavior
  • Describe system constraints
  • Describe system quality attributes
  • Foundation of system design
  • Errors here are expensive to fix later
  • 60%+ of software failures caused by poor requirements
🔍

Requirement Determination

  • Process of discovering, documenting, and understanding user needs
  • Source 1: Users — end users, operational needs
  • Source 2: Managers — reports, dashboards, KPIs
  • Source 3: Stakeholders — customers, suppliers, regulators
  • Source 4: Existing systems — weaknesses, missing features
  • Source 5: Documents — policies, forms, manuals
  • Source 6: External — laws, regulations, standards
✅

Functional Requirements (FR)

  • Describe WHAT the system should do
  • Action-oriented — described using verbs
  • Directly linked to business processes
  • Example: User can log in
  • Example: System calculates total bill
  • Example: System generates invoice
  • "What functions must the system perform?"
⚙️

Non-Functional Requirements (NFR)

  • Describe HOW WELL the system performs
  • Performance: page loads in <3 seconds
  • Security: password encryption
  • Usability: user-friendly interface
  • Reliability: 99.9% uptime
  • Scalability: support 10,000 users
  • Legal: follow data protection laws
🎯

Requirement Gathering Techniques

  • 1. Interviews — direct conversation with stakeholders
  • 2. Questionnaires / Surveys — large groups
  • 3. Observation — watch users work
  • 4. Document Analysis — study existing docs
  • 5. Workshops / JAD — group collaboration
  • 6. Prototyping — build early model
📊

Requirement Analysis

  • Validation: correctness, completeness, feasibility, consistency
  • Techniques: requirement reviews, walkthroughs
  • Techniques: prototyping feedback, stakeholder approval
  • Conflict: conflicting stakeholder needs
  • Ambiguity: vague statements like "fast"
  • Resolution: clarification meetings, modeling, standards
  • MoSCoW prioritization method
Core Concept

Functional vs Non-Functional

This comparison is a high-probability exam topic — know it cold.

🔵

Functional Requirements

  • Describe WHAT the system does
  • Use action verbs (calculate, generate, display)
  • Linked to business processes
  • User can register an account
  • System sends order confirmation email
  • Admin can generate monthly report
  • System validates payment details
  • User can search products by category
🟢

Non-Functional Requirements

  • Describe HOW WELL it performs
  • Quality attributes and constraints
  • Performance: respond in <2 seconds
  • Security: encrypt all passwords with SHA-256
  • Usability: accessible on mobile devices
  • Reliability: 99.9% uptime guaranteed
  • Scalability: handle 10,000 concurrent users
  • Legal: comply with GDPR regulations

Validation & Prioritization

Requirement Analysis

What happens after requirements are gathered — validating, resolving conflicts, and prioritizing.

✅

Validation Ensures

  • Correctness — requirements are accurate
  • Completeness — nothing is missing
  • Feasibility — can actually be implemented
  • Consistency — no contradictions
🔍

Validation Techniques

  • Requirement reviews — formal reading
  • Walkthroughs — step-by-step checks
  • Prototyping feedback — users test early model
  • Stakeholder approval — sign-off from owners
⚠️

Common Problems

  • Conflicting stakeholder needs
  • Vague statements — "the system should be fast"
  • Missing requirements — gaps discovered late
  • Ambiguous language — open to interpretation
  • ✅ Good: "respond within 2 seconds"
  • ❌ Bad: "system should be fast"
🛠️

How to Resolve Conflicts

  • Clarification meetings with stakeholders
  • Requirement modeling — visual diagrams
  • Documentation standards — clear templates
  • Negotiation between conflicting parties
📊

Why Prioritize?

  • Limited budget — can't build everything
  • Time constraints — deadlines
  • Resource availability — team size
  • Focus on highest business value first
🏆

Prioritization Methods

  • MoSCoW — Must/Should/Could/Won't
  • Business Value — ROI focused
  • Risk-Based — high-risk items first
  • Stakeholder Ranking — user importance
  • Must: User login
  • Should: Email notification
  • Could: Dark mode
  • Won't (Phase 1): AI chatbot
